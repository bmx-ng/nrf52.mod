# nRF52840 board bring-up notes

These are the detailed implementation limits and on-board checks behind the concise [coding guide](../README.md#coding-for-nrf52). Hardware results refer to the Tenstar Robot ProMicro nRF52840 unless stated otherwise.

The initial adapter has a 64 KiB static managed arena, a 16 KiB Zephyr main stack, USB CDC standard input and output, and one managed thread. GPIO, GPIO interrupts, hardware random, ADC, PWM, SPI, I²C, polling and buffered UART, watchdog, kernel-managed idle and timed sleep, and a BLE observer/central/peripheral subset are implemented. The Zephyr build reports final flash and RAM use; the hello example is a repeating USB serial greeting.

`BRL.StandardIO.Input` receives bytes from Zephyr's USB CDC console. `examples/nrf52_usb_input.bmx` prompts for `PING`; the board reported `NRF52_USB_INPUT,read=pass` after the Mac sent that word over its USB serial port.

`Embedded.System.Time` uses Zephyr's monotonic uptime and kernel sleeps. The example checks that a 25 ms sleep advances the clock by at least 25 ms and repeats its result over USB serial so a reader can attach after enumeration.

The application overlay enables CDC ACM transmit flow control and a 2 KiB TX FIFO. This keeps consecutive `Print` calls from being discarded when the USB host briefly falls behind; the console may wait for a host that is not reading.

`NRF52.System.Device` reads the eight-byte SoC identifier and captures reset-cause flags through Zephyr's hardware-info driver. Startup saves the flags and clears the hardware register so each subsequent boot has a fresh cause. `examples/nrf52_device.bmx` checks that the identifier remains stable and prints a repeating result over USB serial. `bmk deviceinfo -l nrf52` reports the connected USB mode and, when available, the UF2 bootloader's board information; it cannot obtain the SoC identifier from the generic Zephyr USB descriptor.

`examples/nrf52_memory.bmx` exercises fragmentation, a caught allocation failure, and allocation after collection in the 64 KiB managed arena. Build and flash it like the hello example, replacing the input and output names.

`Embedded.Random` uses Zephyr's `sys_csrand_get()` with the nRF hardware entropy driver and bias correction enabled. A failed entropy request returns failure for buffer fills and stops scalar requests instead of substituting timing data. `examples/nrf52_random.bmx` checks scalar variation, buffer filling, and invalid-argument handling.

`Embedded.Hardware.GPIO` supports digital input/output, pull configuration, standard or high drive strength, and rising/falling or high/low interrupts. `Embedded.Hardware.GPIOEvents` delivers interrupts through a fixed native queue to the managed `PollSystem` event hook. Pins use the SoC numbering: P0.00–P0.31 are 0–31 and P1.00–P1.15 are 32–47. The nRESET pin (18) and USB pins (24, 25) are rejected. The GPIO and interrupt examples exercise P0.15, the board profile's LED pin. Other pin assignments are carrier-dependent; verify them before attaching external hardware. The nRF hardware has two symmetric drive modes, mapped to portable Low and Maximum; Medium and High return false.

`Embedded.Hardware.ADC` supports the eight SAADC inputs on P0.02–P0.05 and P0.28–P0.31, with 12-bit raw readings. The ADC example verifies initialization and bounded readings on P0.02. It does not measure accuracy against a known voltage. `Embedded.Hardware.PWM` exposes independent PWM0 and PWM1 channels on the LED P0.15 and the exposed D4 / P0.22 pad. The Zephyr PWM API uses board-defined pin routing, so other pins are unavailable until added to a board profile. Do not claim the same pin through GPIO, ADC, or PWM at the same time.

`examples/nrf52_pwm.bmx` verified independent channel settings on the Tenstar board, reporting `NRF52_PWM,frequency=pass,duty=pass,polarity=pass,independent=pass`. `examples/nrf52_pwm_loopback.bmx` checks the physical D4 output by connecting D4 / P0.22 to D3 / P0.06 and counting edges. On the Tenstar board it repeatedly reported `NRF52_PWM_LOOPBACK,transitions=pass,count=28`.

`Embedded.Hardware.SPI` exposes the board's SPI2 controller as portable controller 0. The default pins are SCK P1.01 (33), MOSI P1.02 (34), and MISO P1.07 (39); a build overlay can select another route; chip select is controlled separately through GPIO. The hardware transfers bytes, so 16-bit API calls transfer each word as two host-order bytes. Requested rates from 125 kHz to 8 MHz round down to a supported hardware rate. `examples/nrf52_spi.bmx` checks a physical MOSI-to-MISO loopback, including 8-bit and 16-bit calls. The alternate D15-to-D14 route passed the same loopback on the Tenstar board. Verify the clone's pad labels before wiring.

`Embedded.Hardware.UART` exposes UART0 as portable controller 0, with default TX P0.09 (D10), RX P0.10 (D16), RTS P0.06 (D3), and CTS P0.08 (D2). A build overlay can select another route. The default controller is unavailable because standard output uses USB CDC. The adapter supports 8 data bits, one stop bit, no or even parity, polling transfers and timed reads. Polling reads use a small asynchronous receive ring because Zephyr disables `uart_poll_in` when its asynchronous UART driver is enabled. UART initialization waits for the receive-start event before returning, so an immediate first byte can be received. `Embedded.IO.BufferedUART` uses the same driver with a pair of receive DMA buffers and native 512-byte maximum receive and transmit rings; opening and closing a buffered stream transfers receive ownership between the two APIs. Requested stream capacities must be powers of two between 2 and 512. Do not mix polling reads or writes with an open buffered stream on the same controller. Applications using a buffered stream must import a system event driver such as `BRL.EventQueue`. Hardware flow control requires both RTS and CTS; enabling only one returns false. TX break is unavailable. `examples/nrf52_uart.bmx` checks a polling D10-to-D16 loopback; `examples/nrf52_buffered_uart.bmx` checks a 96-byte buffered loopback across two transmit blocks; and `examples/nrf52_uart_flow.bmx` checks hardware flow control with D10 connected to D16 and D3 connected to D2. All three checks passed on the Tenstar board. The flow-control check also verified that a one-sided request is rejected and that a 96-byte buffered transfer succeeds with RTS/CTS enabled.
The alternate UART build route in `examples/nrf52_uart_alt.overlay` passed an eight-byte 115200 baud loopback with D6 connected to D7 on the Tenstar board. The first image did not enumerate on USB; a diagnostic image with startup prints did enumerate and passed. The initial non-enumeration has not been isolated further.

`Embedded.Hardware.I2C` maps portable controller 0 to Zephyr I²C1, which is independent of UART0. Its default pins are SDA P1.04 (D8) and SCL P1.06 (D9); a build overlay can select another route. The overlay enables the nRF's internal pull-ups, so `I2CConfigurePins` requires `pullUps=True`; short connections can use these pull-ups, while longer or higher-capacitance buses may need external pull-ups. The adapter supports 100 and 400 kHz, blocking writes and reads, and a combined write/read with repeated Start. Zephyr's nRF driver uses a build-time 20 ms timeout for each message. Timed calls reject requests shorter than that limit (40 ms for combined write/read), but a longer requested timeout does not extend the driver's limit. Therefore these calls do not yet offer a true caller-selected deadline. `examples/nrf52_i2c.bmx` targets address `$42` and expects the four-byte reply `NRF!`. An ESP32-S31 responder project for this example is in `tests/targets/esp32_s31_i2c_target`.

### Peripheral follow-up

UART, SPI, and I²C now accept build-time routes through a devicetree overlay, with checks for function ordering, reserved pins, and collisions with other configured peripherals. Runtime pin reassignment is not supported because Zephyr initializes these devices before application code runs. PWM likewise has only two routed outputs today (LED and D4); additional channels need explicit board-profile assignments and a physical output check. I²C caller-selected deadlines need driver-level timeout control; a wrapper around a blocking transfer cannot safely return while that transfer still uses the caller's buffer. UART TX break is unsupported by the current nRF UARTE path. ADC accuracy against a known voltage and electrical behavior with external I²C pull-ups remain hardware checks.

On the Tenstar board, the I²C example passed against an ESP32-S31 Function CoreBoard-1 with nRF D8 connected to the ESP pin printed `0`, nRF D9 to the ESP pin printed `1`, and a common ground. The alternate build-time route also passed with nRF D7 connected to ESP GPIO0 and nRF D19 to ESP GPIO1. Both boards were powered separately over USB; the nRF printed `NRF52_I2C,write=pass,read=pass,restart=pass` repeatedly. The ESP pin labels are GPIO numbers, not connector position numbers.

`Embedded.System.Power` advertises idle and timed sleep. `PowerIdle` sleeps the calling managed thread for one kernel tick so Zephyr's idle thread can run. `LowPowerSleep` uses Zephyr's timed thread sleep; zero and durations above the kernel's signed 32-bit limit are rejected. The nRF52840's System OFF mode restarts the program on wake, so it does not satisfy the portable dormant-sleep contract, which must return to the same program. System OFF also has no timer wake source. Interrupt-only sleep and automatic low-leakage pin configuration report unavailable until the adapter can identify a safe wake event and pin ownership. The `exclusive` argument has no separate effect in this Zephyr adapter. `examples/nrf52_power.bmx` verified the capability mask, validation and clock advance on the Tenstar board. No current measurement or USB suspend test has been made, so this establishes API behavior rather than a measured power reduction.

`NRF52.System.Power` exposes the distinct `SystemOff()` and `SystemOffUntilGPIO(pin, activeHigh)` operations. Both stop the current program and restart through the bootloader after a wake event; a successful call never returns. The GPIO form configures a valid, otherwise unused pin as a sense input with a pull toward its inactive level and rejects a pin that is already active. Save application state before entering System OFF and inspect `NRF52.System.Device.ResetCauseFlags()` during the next boot, while allowing for bootloader and wake-source differences. There is no timer wake in System OFF on this SoC. `examples/nrf52_system_off.bmx` waits for an explicit USB command before entering this mode, avoiding an automatic sleep loop on reboot. On the Tenstar board, `SystemOff()` disconnected USB and remained off with the cable attached until RST was briefly grounded; the next boot reported reset cause 0. `SystemOffUntilGPIO(22, False)` also disconnected USB and remained off, then a brief D4 / P0.22-to-GND connection restarted the board. That boot reported `ResetCauseLowPowerWake` (128). The invalid nRESET pin was rejected before either call. No current measurement has been made, so these checks verify entry and wake behavior only.

`NRF52.Hardware.Watchdog` exposes the portable watchdog API through Zephyr. The nRF hardware watchdog cannot be disabled once started; `WatchdogDisable()` then returns false and a power cycle stops it. `examples/nrf52_watchdog.bmx` arms a five-second timeout only after a reset-pin boot, checks feeding and disable behavior, and never rearms unless the reset-pin flag is present. On the Tenstar board it restarted once and repeatedly reported `NRF52_WATCHDOG,reset=pass,cause=16`, the watchdog flag alone. Capturing and clearing the reset-cause register at application startup resolved the earlier ambiguity without changing the UF2 bootloader.

`NRF52.Network.BLE` implements a peripheral, observer, and central-connection subset of `Embedded.Network.BLE` through Zephyr. It supports initialization, active and passive scanning, duplicate-filter selection, timed or explicit scan completion, outbound connections and cancellation, connectable or nonconnectable advertising, up to four dynamic GATT services and eight readable and/or writable characteristics of up to 512 bytes each, value access, managed connection, write, subscription, and update-completion events, and disconnect/connection information. Importing the module selects `cmake/application/ble.conf` automatically. GATT client service, characteristic, and descriptor discovery plus bounded read/write are implemented. The security API supports pairing, bond storage in the UF2 board's settings partition, bond enumeration and deletion, security events, passkey callbacks, and encrypted or authenticated GATT permissions. `secureConnectionsOnly=True` rejects legacy pairing and disconnects links that do not negotiate Secure Connections. Zephyr always offers Secure Connections in this build, so `BLEConfigureSecurity` returns `-100` for `secureConnections=False`. Scan results use a bounded 32-event native queue, with eight slots reserved for connection, security, and completion events while scanning; `BLEDroppedEvents()` reports discarded scan results or other overflow in crowded radio conditions. The Zephyr image for `examples/nrf52_ble_gatt.bmx` with pairing enabled uses 295,176 B flash (36.40% of the 792 KiB app partition) and 156,896 B RAM (59.85% of 256 KiB). On the Tenstar board, an ESP32-S31 client in `tests/targets/esp32_s31_ble_gatt_client` discovered service `FFF0` and characteristic `FFF1` by UUID, read `NRF!`, wrote `PING`, read it back, and disconnected. The nRF received the write event and resumed advertising. The ESP32's original app was restored after the test.

`examples/nrf52_ble_notify.bmx` adds a Client Characteristic Configuration descriptor to the `FFF1` characteristic and pushes `PUSH` when a client subscribes. `tests/targets/esp32_s31_ble_notify_client` discovers the descriptor by UUID, enables notifications, and verifies the value over the air. The nRF reported subscription and notification completion, and resumed advertising after disconnect. This image uses 207,180 B flash (25.55%) and 119,068 B RAM (45.42%). The ESP32's original app was restored again with hash verification and its `GC_STAGE2_STRESS` self-check passed.

`examples/nrf52_ble_indicate.bmx` sends `ACK!` after an indication subscription. The ESP32-S31 client in `tests/targets/esp32_s31_ble_indicate_client` discovers the CCC descriptor, subscribes to indications, receives `ACK!`, and confirms it. The nRF emitted `EVENT_BLEGATTUPDATECOMPLETE` with confirmation and resumed advertising after the client reset. This image uses 207,660 B flash (25.61%) and 119,580 B RAM (45.62%). A characteristic may retain its last value between connections; the test reads but does not require a particular pre-subscription value. The ESP32's original app was restored with hash verification and its `GC_STAGE2_STRESS` self-check passed.

`examples/nrf52_ble_scan.bmx` exercises the shared scan events using `tests/targets/esp32_s31_ble_advertiser`, whose name is deliberately placed in its scan response. Zephyr's legacy scanner does not apply its controller timeout without extended advertising, so the adapter enforces the requested duration while pumping events. A zero duration scans until `BLEStopScan()` is called. Timed scans above the kernel's signed 32-bit millisecond range return `-EINVAL`. Scan completion is delivered while the application polls system events. On the Tenstar board with the ESP32-S31 test advertiser, a filtered active scan received `ESP Scan Target` in a scan response; a filtered passive scan did not receive its name; and an untimed unfiltered scan saw 13 named responses before `BLEStopScan()` emitted completion with scanning inactive. The final image uses 211,612 B flash (26.09%) and 132,764 B RAM (50.65%).

`examples/nrf52_ble_central.bmx` scans for the ESP32-S31 test advertiser, connects from the nRF central role, checks peer address and MTU, then disconnects and repeats. The ESP32 target resumes advertising on disconnect. Zephyr is configured for one connection, so advertising and outbound connecting cannot run concurrently. The Tenstar board completed five central connect/disconnect cycles against the ESP32-S31 with the final image, reporting role 0, the peer address, and an ATT MTU of 23. The test image uses 223,228 B flash (27.52%) and 132,892 B RAM (50.69%).

`examples/nrf52_ble_gatt_client.bmx` connects to `tests/targets/esp32_s31_ble_gatt_server`, discovers service `FFF0`, characteristic `FFF1`, and descriptor `FFF2`, reads `ESP!` and `DSC`, writes `PING`, reads it back, and disconnects. The Tenstar board reported every stage passing. The image uses 233,388 B flash (28.78%) and 133,980 B RAM (51.11%). Client requests are serialized per operation type, read results are capped at 512 bytes, and writes longer than the current ATT MTU minus three bytes return `-EMSGSIZE`; long writes, write-without-response, nonzero read offsets, and concurrent client operations have not yet been exercised on the board.

`examples/nrf52_ble_probe.bmx` remains a lower-level radio bring-up check. Build it with `BMX_NRF52_EXTRA_CONF_FILE` set to the absolute path of `examples/nrf52_ble_probe.conf`.

The target files live in the top-level `nrf52.mod` module root, matching `pico.mod` and `esp32.mod`. Public nRF52-specific APIs use `NRF52.Runtime`, `NRF52.System.Time`, `NRF52.System.Device`, and `NRF52.IO.StandardIO`. Cross-target contracts remain in `Embedded.*`.

`examples/nrf52_ble_notify_client.bmx` subscribes as a central to the ESP32-S31 target in `tests/targets/esp32_s31_ble_notify_server` through `TBLEClientDescriptor.SetSubscription`. The nRF adapter maps a discovered `2902` CCC descriptor to Zephyr's client subscription callback and emits the shared `EVENT_BLENOTIFICATION`. On the Tenstar board, subscription completed, `PUSH` arrived intact, and disconnect passed: `NRF52_BLE_NOTIFY_CLIENT,subscribe=1,notify=1,disconnect=pass`. The image uses 233,004 B flash (28.73%) and 134,044 B RAM (51.13%). The ESP32 original app was restored with hash verification and passed `GC_STAGE2_STRESS`.

`examples/nrf52_ble_client_subscription.bmx` verifies central-side MTU exchange, notification, unsubscribe, indication, and disconnect against the ESP32-S31 target in `tests/targets/esp32_s31_ble_notify_server`. The Tenstar board reported `NRF52_BLE_CLIENT_SUBSCRIPTION,mtu=23,notify=1,unsubscribe=1,indicate=1,disconnect=pass`. The image uses 234,460 B flash (28.91%) and 134,044 B RAM (51.13%).

`examples/nrf52_ble_connection_controls.bmx` checks connection signal strength, current and requested PHY, and a connection interval update against the same peer. Enabling Zephyr's controller RSSI option made the signal strength query work; the board reported about -31 dBm. Zephyr returned `-EACCES` for interval and PHY requests made during early link setup, so the example waits and retries. The final diagnostic received a successful connection update event and a 2M PHY update event, then disconnected. The compiled image uses 235,644 B flash (29.06%) and 134,236 B RAM (51.21%). The ESP32 original app was restored with hash verification and passed `GC_STAGE2_STRESS`.

`examples/nrf52_ble_bulk_client.bmx` exercises the larger ATT buffers against `tests/targets/esp32_s31_ble_bulk_server`. The nRF negotiated MTU 247, read a 300-byte characteristic, read 250 bytes from offset 50, wrote 300 bytes through Zephyr's prepare/execute path, read them back, sent a 16-byte write without response, read it back, and disconnected. Every stage passed on the Tenstar board. The nRF image uses 241,064 B flash (29.72%) and 140,776 B RAM (53.70%). The adapter now emits write completion for write without response from Zephyr's transmission callback and supports response writes up to the 512-byte API bound.

`examples/nrf52_ble_dual_notify_client.bmx` discovers two notifying characteristics in the ESP32-S31 test service, subscribes to both, receives updates from each, proves the first remains active while the second starts, unsubscribes from both, and disconnects. The Tenstar board reported `NRF52_BLE_DUAL_NOTIFY,first=1,second=1,overlap=1,unsubscribe=pass,disconnect=pass`. The image uses 241,144 B flash (29.73%) and 141,032 B RAM (53.80%). The native client keeps up to eight independent subscription records.

`examples/nrf52_ble_lifecycle.bmx` checks nonconnectable and connectable advertising start and stop, cancels a pending connection to an absent peer, scans after cancellation, disables and re-enables BLE, and scans again. The Tenstar board reported every stage passing: `NRF52_BLE_LIFECYCLE,advertising=pass,cancel=pass,scan=pass,reinitialize=pass`. The image uses 239,720 B flash (29.56%) and 141,032 B RAM (53.80%).

`examples/nrf52_ble_long_gatt_server.bmx` exposes a 512-byte-capacity local characteristic. The ESP32-S31 peer in `tests/targets/esp32_s31_ble_long_gatt_client` negotiated MTU 247, wrote a 300-byte pattern through prepare/execute writes, read all 300 bytes back, and disconnected. The nRF reported `NRF52_BLE_LONG_GATT_SERVER,write_300=pass` and `disconnect=pass`; the ESP32 reported `S31_LONG_GATT,mtu=247,write_300=pass,read_300=pass` and `disconnect=pass`. The nRF image uses 240,048 B flash (29.60%) and 143,740 B RAM (54.83%). Zephyr now reserves four prepare-write buffers and validates each fragment against the characteristic capacity before applying the assembled write.

`examples/nrf52_ble_advertising_service.bmx` checks a 350 ms nonconnectable advertisement ends with `EVENT_BLEADVERTISINGCOMPLETE`, then starts indefinite advertising for the ESP32-S31 scanner in `tests/targets/esp32_s31_ble_scanner`. The nRF reported `NRF52_BLE_ADV_SERVICE,timed=pass,advertising=pass`, and the ESP32 saw the `FFF0` service UUID in the primary advertisement: `NRF52_BLE_ADV_SERVICE,uuid16=pass`. The nRF image uses 240,384 B flash (29.64%) and 143,740 B RAM (54.83%). The adapter includes the selected local service UUID in advertising data and enforces finite durations while the application pumps BLE events.

The client now keeps subscription records scoped to a connection and reports `-ENOSPC` if more than eight CCC descriptors are discovered. On a central disconnect, pending discovery, read, write, and MTU requests receive `-ENOTCONN` completion events so the managed API does not retain a busy request. The read path also maps Zephyr's generic GATT error to `-ENOTCONN` when the connection is already closing; a local disconnect during a pending read follows the same rule. `examples/nrf52_ble_disconnect_during_read.bmx` was tested against `tests/targets/esp32_s31_ble_drop_server`: the ESP32 held a read open and was reset while the nRF request was pending. The nRF reported `NRF52_BLE_DROP_DURING_READ,mtu=247,interrupted_read=pass,reconnect=pass,read_300=pass,disconnect=pass`. On this Zephyr ARM toolchain, `-ENOTCONN` is `-128`.

`examples/nrf52_ble_multi_gatt.bmx` creates two local services (`FFF0`, `FFE0`) with three characteristics (`FFF1`, `FFF2`, `FFE1`). The ESP32-S31 peer in `tests/targets/esp32_s31_ble_multi_gatt_client` discovered both services and all three characteristics, read their initial values, wrote `UP!` to `FFF2`, read it back, and disconnected. The nRF reported `NRF52_BLE_MULTI_GATT,write_second=pass` and `disconnected=pass`; the ESP32 reported `S31_MULTI_GATT,services=2,characteristics=3,reads=pass,write_second=pass` and `disconnect=pass`. The ESP32 original application was restored and passed its self-check.

`examples/nrf52_ble_security.bmx` configures Just Works bonding and an encrypted-read characteristic. The ESP32-S31 peer in `tests/targets/esp32_s31_ble_security_client` paired, read the protected value, disconnected, and reconnected repeatedly. The nRF reported encryption with a 16-byte key and one bond; the ESP32 reported `S31_SECURITY,protected_read=pass`. After reloading a revised nRF image, `bonds_at_start=1` confirmed the bond persisted in flash. The ESP32 original application was restored and passed its self-check.

`examples/nrf52_ble_passkey.bmx` uses Keyboard Only authentication, Secure Connections only, and a characteristic that requires authenticated reads. On startup it enumerates an existing bond, then deletes bonds before pairing. The ESP32-S31 peer in `tests/targets/esp32_s31_ble_passkey_client` displays a fixed test passkey; the nRF receives an input action and supplies it through `BLEProvidePasskey`. Both boards reported authenticated pairing, the ESP32 read the protected value, and the nRF stored one new bond. The passkey `123456` is solely for this hardware check; applications should use fresh passkeys.

`examples/nrf52_ble_numeric.bmx` tests numeric comparison through `BLEConfirmPasskey` and deletion of an individual bond through `TBLEBond.Forget()`. The ESP32-S31 peer in `tests/targets/esp32_s31_ble_numeric_client` accepted the displayed comparison. The nRF reported `confirmed=pass`, authenticated encryption with a 16-byte key, one new bond, and advertising stopped after disconnect; the ESP32 read the authenticated characteristic. The automatic confirmation is solely for the board test; an application should ask its user to compare both displayed numbers before accepting.

`examples/nrf52_ble_rejected_pairing.bmx` rejects the first numeric comparison, checks that the failed attempt saves no bond, then accepts a fresh attempt. The ESP32-S31 client in `tests/targets/esp32_s31_ble_rejected_pairing_client` observed the rejection, reconnected, paired, and read the authenticated characteristic. On the Tenstar board the nRF reported `rejected=pass,bonds=0` followed by `retry=pass,bonds=1`; the ESP32 reported `rejected_then_retry=pass`. The test image uses 299,600 B flash (36.94%) and 157,024 B RAM (59.90%). The ESP32 original app was restored with flash hash verification and passed its `GC_STAGE2_STRESS` self-check. The test's automatic comparison response is only for this controlled pairing check.

`examples/nrf52_ble_protected_access.bmx` requires authenticated access for characteristic writes and notification subscriptions. The ESP32-S31 peer in `tests/targets/esp32_s31_ble_protected_client` first received ATT authentication errors for both operations (status 261), then paired with numeric comparison, wrote `UP!`, subscribed, and received `PUSH`. The nRF reported the authenticated write, subscription, and notification completion; the ESP32 reported `S31_PROTECTED,complete=pass`. The image uses 299,960 B flash (36.99%) and 157,024 B RAM (59.90%). The ESP32 original app was restored with flash hash verification and passed its self-check. Both boards automatically accept numeric comparison only for this controlled test.

`examples/nrf52_ble_limits.bmx` fills the four-service and eight-characteristic GATT allocation, verifies that further additions fail, then scans without consuming events for seven seconds against the ESP32-S31 advertiser. The Tenstar board reported `services=4,characteristics=8,capacity=pass` and `scan_results=23,dropped=259,completion=pass`. This confirms scan traffic is discarded when the reserved queue capacity is reached while scan completion remains deliverable. The image uses 298,436 B flash (36.80%) and 156,960 B RAM (59.88%). The ESP32 original app was restored with flash hash verification and passed its self-check.
